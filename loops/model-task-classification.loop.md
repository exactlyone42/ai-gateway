## 目的
讓 Gateway 先判斷工作種類，再挑真正適合且可用的模型；每次選擇都能在後台看懂及修正。

## 完成判準
- [ ] 任務分類、必要能力、服務目標分開保存並有版本；品質等級只保留舊 Client 相容用途。
- [ ] 模型可設定擅長任務、必要能力、成本、延遲、資料來源、信心與人工覆寫；每次修改都有紀錄。
- [ ] 路由順序固定為：必要能力排除 → 任務分類 → 形成短名單 → Jev 獨立複核 → 依健康、成本與延遲選擇。
- [ ] 分類器或 Jev 沒有結果時，沿用 Client 原始模型；Gateway 不在同一請求偷偷改用另一供應商重送。
- [ ] 後台可查看及修改模型分類，並看見原始模型、分類理由、Jev 意見、最後模型與改選理由。
- [ ] 先用旁路模式量測，不改真實路由；案例集固定版本，報告分類準確率、Jev 同意率、fallback、成功率、延遲與成本。
- [ ] 現有模型資料完成可重跑的轉換，不再把全部 Claude 模型統稱為 premium。
- [ ] 格式、靜態檢查、單元、整合、瀏覽器與正式站版本讀回全過。
- [ ] 陰性對照：錯誤能力、相似描述、分類逾時、Jev 無結果、跨身分資料與舊 premium 資料，對應測試必須變紅。

## 已知

## 已確定不可行
- 只用 economy／standard／advanced／premium 排所有模型：一個數字無法同時表示任務能力、成本與速度。
- 把分類器寫死為某個 Claude 名稱：模型清單會更新，應由後台設定角色並保留退回路徑。

## 證據
- 正式資料庫查詢：啟用模型的品質分布為 premium 16、standard 4；證明現況混在一起，不證明新分類準確。
- `loops/model-routing-admin.loop.md`：既有能力過濾與 Jev 退回契約；仍須以執行路徑及測試重新驗證。

## Trade-off
| 決策 | 選了什麼 | 放棄了什麼 | 為什麼 |
| --- | --- | --- | --- |
| 主分類 | 任務適合度＋硬能力 | 單一品質排名 | 不同工作需要不同能力 |
| 分類模型 | 後台指定角色 | 寫死 Fable／Opus | 可換模型且能停用 |
| 上線 | 先旁路量測再啟用 | 直接改正式路由 | 先取得真實誤判率 |
