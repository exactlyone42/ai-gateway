# Claude Code 工作跑滿 15 分鐘卻沒有產物

## 一句話結論

這次不是 Claude Code 單純太慢，也不是「工作區未受信任」警告造成。Gateway 同一時間只准一個 Claude 請求執行，其他請求等 30 秒後被拒絕；部署又在工作途中重啟 Gateway，關掉了一個仍在進行的請求。Claude Code 不斷重試，最後整個工作跑滿 15 分鐘，卻來不及寫出檔案。

## 使用者看到什麼

- Claude 程序一直在執行，但沒有產生 `design/gdd/combat.md` 和 `design/gap-report.md`。
- 外層的 `timeout 900` 最後回傳 124。白話說，就是工作超過 15 分鐘，被外層強制停止。
- 日誌只留下「工作區未受信任」警告。這個警告會讓專案自己的權限設定失效，但現有證據沒有顯示它阻止了請求或檔案寫入。

## 實際發生什麼

2026-10-21 13:05–13:20，Gateway 收到 50 個 Claude 請求：

| 結果 | 次數 | 白話意思 |
| --- | ---: | --- |
| 成功完成 | 27 | Claude 有正常回答 |
| 等待超過 30 秒 | 10 | Gateway 沒有空位，直接拒絕 |
| 呼叫端等 60 秒後離開 | 11 | 回答還沒完成，Claude Code 已放棄這次連線 |
| 模型能力不符 | 2 | 該次要求的能力與可用模型不相容 |

13:12:46 部署程序要求 Gateway 重啟。當時仍有 1 個請求在執行；Gateway 等了 30 秒，於 13:13:16 關掉該連線，再啟動新版本。

## 根因

### 根因一：可同時執行的請求被設成 1

正式設定把同一憑證、模型與供應來源的同時執行上限都設成 1。Claude Code 會同時做讀檔、分析及工具工作，因此第一個慢請求會讓後面的請求全部排隊。排隊超過 30 秒後，Gateway 回覆逾時。

### 根因二：工作進行中仍直接部署

部署發生時仍有請求在跑。Gateway 已經等候 30 秒，但該請求沒有在期限內結束，因此被強制關閉。這證明「服務重新啟動成功」不等於「使用者正在進行的工作沒有受影響」。

### 放大問題：呼叫端 60 秒後放棄

11 個請求都在約 60 秒時由呼叫端中止。這讓長回答無法完成，並觸發更多重試。60 秒限制位於哪一層仍需另行查證，不能先認定是 Claude Code 或 Gateway。

### 12:07 的「Connection lost」已查清

Claude Code 在 12:06:00.548 送出請求，Gateway 在 12:06:01.041 選好 Claude，
但上游約 58 秒沒有回傳可交給 Client 的資料。Claude Code 在整筆請求滿 60 秒時關閉連線。
Caddy 的同一筆紀錄只維持 1.544 秒，且設定沒有讀取逾時，因此不是 Caddy 切斷。

根因是 Gateway 的模型清單沒有告訴 Claude Code 這條路徑可能長時間靜默，本機 Claude
也沒有提高靜默等待時間。供應商偶發慢到第一筆資料接近 60 秒時，就會被誤判成斷線。

另有一個獨立放大問題：供應商回覆一次 429 後，Gateway 會把該供應商暫停 30 秒，
讓後續本可交給供應商判斷的請求改由 Gateway 回 503。

## 解決方法

### 立即處理

1. 在調整前，不要用這條 Gateway 路徑重跑長時間、多步驟工作。
2. 沒有進行中的請求時才部署，避免再次切斷工作。
3. 依主機與 Claude 帳號實測結果，提高同時執行上限；不能直接猜一個很大的數字。

### 永久修正

1. 建立模擬 Claude Code 同時送出多個請求的壓力測試，量出成功率、等待時間與主機負載，再決定安全上限。
2. 部署前先停止接新工作，等待舊工作完成；超過安全期限就取消本次部署，而不是切斷使用者工作。
3. 將「30 秒排隊逾時」「60 秒連線中止」「部署時仍有請求」變成自動告警。
4. 發版驗收加入長工作測試：工作進行中部署，必須能完成原工作，或部署應自動延後。
5. 後台顯示目前執行數、排隊數、最久等待時間及近一小時的逾時數，讓問題不必靠翻日誌才看得見。

## 如何保證不再發生

「提高上限」不是保證。完成以下自動檢查，才算真正修好：

- 同時送出多個模擬請求，全部在約定時間內完成，沒有 30 秒排隊逾時。
- 長請求執行時觸發部署，請求不中斷；若無法安全部署，部署自動取消並告警。
- 故意把同時執行上限降回 1，上述測試必須失敗，證明測試真的抓得到這個問題。
- 連續觀察實際流量，排隊逾時與部署中斷維持為 0。

## 證據與邊界

證據來自 `agent-gateway-jev.service` 在 2026-10-21 13:05–13:20 的實際服務日誌，以及正式設定中的同時執行上限。日誌能證明 Gateway 拒絕、連線中止與部署中斷；它不能證明 60 秒限制究竟由 Claude Code、網路轉送層或 Gateway 哪一層設定。

## 2026-10-21 立即修正結果

最初先把同時執行上限由 1 提高為 8，但這仍是 Gateway 自行限制請求，不符合產品目的，因此改為完全略過 Gateway 的同時請求限制。請求會直接送往選定的供應商，由供應商或模型能力決定是否拒絕。

實際同時送出 4 個 Claude 請求，4 個都在 5 秒內完成，沒有錯誤，也沒有排隊 30 秒後被拒絕。自動測試另以原本會限制為 1 的設定連續取得 100 個執行資格，全部通過，證明 Gateway 不再以自身同時請求上限攔截。忙碌時自動延後部署的永久保護仍未完成。

## 2026-10-21 第二次永久修正

- 模型清單對每個模型宣告可等待 600 秒，且自動重送為 0；本機 Claude Code 同步啟用
  Gateway 模型發現並把靜默等待提高為 600 秒。
- 供應商 429 不再讓 Gateway 暫停供應商；429 原樣回給該次呼叫，下一次請求仍送出。
- 自動測試鎖定兩項行為：模型清單必須回傳等待設定；一次 429 後，唯一供應商仍可被選中。
- Client 收到供應商回應標頭前，Gateway 無法安全偽造串流資料，否則無法原樣轉送供應商錯誤。
  因此用 Client 官方等待設定預防，而不是偽造回應。
