# 任務記帳

每個段落記：開始、結束、token 用量、以及當初的 trade-off。

**token 一律實測，不估算。** 估算不可稽核，也無法用來改進工作方式。

## 怎麼記

1. 段落開工時，在 `loops/<slug>.loop.md` 的表格填 `開始`（ISO 8601，含時區）。
2. 收工時填 `結束`。
3. 跑 `./scripts/token-ledger.sh --slug <slug> --md`，把輸出那一列貼進下面的表。

腳本從 Claude Code 的對話紀錄（`~/.claude/projects/*agent-pool-gateway*/*.jsonl`）
按時間窗加總，用 `requestId` 去重（同一則訊息在串流過程會被寫入多次，不去重會重複計算），
並按 Agent 分項——子 Agent 的用量也算進來。

未填 `結束` 時，腳本量到「現在」，可以中途查。

## 可攜性：換掉 Claude Code 之後怎麼辦

### 現在有哪些東西綁死 Claude Code

| 項目 | 綁死程度 | 換 agent 之後 |
| --- | --- | --- |
| `scripts/token-ledger.sh` | **完全綁死**。它讀 Claude Code 的對話紀錄檔 | **直接失效** |
| `CLAUDE.md` 這個檔名 | 慣例綁定 | 改檔名即可（Codex 讀 `AGENTS.md`，Cursor 讀 `.cursorrules`），內容照抄 |
| `start-work`／`cashloop` skill | 完全綁死 | 失效，但方法本身寫在文件裡，人可以照做 |
| `scripts/check.sh`、`check-selftest.sh` | **不綁**。純 bash，CI 直接跑 | 照常 |
| loop 檔、`docs/`、看板流程 | **不綁**。純 markdown ＋ `gh` | 照常 |

換句話說：**品質關卡與工作紀律都不綁 agent，只有「量 token」這件事綁。**

### 而且它連在 Claude Code 上都沒有保證

那些對話紀錄是**未公開的內部格式**，不是對外 API。Claude Code 改版就可能改掉。
所以這個讀取器**現在能用是實測出來的，不是保證**。

因為這樣，腳本在時間窗內找不到任何紀錄時**回報失敗（exit 3），不回報 0**。
「這段時間沒用量」和「讀取器壞了」印出來的零長得一模一樣，
拿零當量測結果就是規範第 3 節禁止的那種假綠。

### destination：閘道自己就是 token 帳本

**這個腳本是鷹架，不是終點。**

W05 做完以後，我們自己的開發流量就指向這個閘道。閘道本來就會把每一次請求的
token 用量寫進 PostgreSQL，而且帶著身分（人／設備／Client／Agent）。
到那時候，任務記帳改成查閘道自己的 `usage_records`，這支腳本就可以刪掉。

這樣做有三個好處：

1. **不綁任何 agent。** Claude Code、Codex、Cursor、自建 Agent，只要走閘道就算得到。
2. **格式是我們自己的 schema**，不會被別人改版改掉。
3. **順便就是 dogfooding** —— 我們每天都在用自己的帳本，帳不準會第一個發現。

**在 W05 之前不要先蓋抽象層。** 只有一個來源時做多來源介面，是為假想需求寫程式碼。
現在做的只有兩件：把依賴寫在腳本開頭，以及讓它壞掉時大聲失敗。

## Token 節約：從實測數字得到的規則

`gateway-blueprint` 開工 45 分鐘後的實測分佈：

| 種類 | Token | 佔比 |
| --- | --- | --- |
| 快取讀取（cache_read） | 16,796,134 | 94.7% |
| 快取寫入（cache_write） | 731,722 | 4.1% |
| 輸出（output） | 215,497 | 1.2% |
| 輸入（未快取） | 252 | ~0% |

**成長曲線比佔比更有意思**。同一個 session 的 `main` 分項：

| 時點 | 累積工具呼叫 | 累積 billed |
| --- | --- | --- |
| 開工 29 分 | 78 | 8.7M |
| 開工 45 分 | 126 | 17.7M |
| 開工 ~90 分 | 163 | 26.4M |

呼叫數 78→126（1.6 倍）時 billed 變 2.0 倍；126→163（1.3 倍）時再變 1.5 倍。
因為每一次呼叫都重讀**當下**的整個對話，而對話本身一直在長
→ 成本大致隨「回合數 × 平均 context 長度」成長，**愈到後期每一回合愈貴**。

**這證明**：成本的主體是「把既有 context 重讀一遍」，不是「產出」。
**回合數**比**輸出長度**貴得多，而且愈到後期每一回合愈貴。
**證明不了**實際金額——不同 token 種類費率不同，本腳本不換算金錢。

由這組數字得出的規則：

1. **合併獨立的工具呼叫。** 同一個回合裡平行發出的多個呼叫只重讀一次 context；
   拆成多回合就重讀多次。這是最大的單一節約手段。
2. **子 Agent 用在「廣搜、只要結論」**。一個子 Agent 起手就多一份完整的 cache_write
   （實測 144k／244k／60k），但它讀的幾十頁文件不會進主 session 的 context——
   而主 session 的 context 每一回合都要重讀一次，所以省下的是「污染 × 剩餘回合數」。
   判斷標準：**要讀的原始資料量 > 起手成本**才划算。查一個已知檔案的一個值，自己讀更省。
3. **不要重讀已經讀過的檔案。** 改完檔案不要為了「確認」再讀一次——編輯失敗會直接報錯。
4. **只讀需要的片段**。大檔案用 `sed -n` 取範圍，不要整份載入。
5. **搜尋用 `grep`／`find` 取行，不要載整個目錄。**
6. **不要重述已經確立的事實。** 重複敘述會進 context，之後每一回合都要重讀一次。
7. **loop 檔主體壓在 200 行內**，本身就是 token 紀律：現況檔會被反覆讀，寫得散就反覆貴。
